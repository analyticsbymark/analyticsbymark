    Statsig Experimentation Implementation Plan

    Architecture Overview

    Design Philosophy: Cache-First, No Hiding

    Our experiment system uses synchronous cache-first initialization. On a user's first visit, they see the default content rendered in the DOM. The Statsig SDK initializes synchronously from localStorage cache (empty on first visit), then refreshes in the background. On subsequent visits, cached experiment values are applied instantly — no delay, no flicker.

    Key principle: We do NOT use data-hidden or any anti-flicker hiding. Default content is always visible. Experiments are a progressive enhancement applied from cache.

    How It Works

    First visit:
1. Page renders with default DOM content (visible immediately)
2. initializeSync() → empty cache → fallback to DOM defaults
3. Background: initializeAsync() → fetches from Statsig → saves to localStorage

Subsequent visits:
1. Page renders with default DOM content
2. initializeSync() → loads cached values → applies variant instantly
3. Background: initializeAsync() → refreshes cache for next visit

    Fallback Hierarchy

    1. Cached experiment value (localStorage, populated by previous visit)
   ↓
2. DOM default content (already rendered, always visible)

    No blocking, no hiding, no flicker management needed.

    js/statsig/

│   └── experiments.config.template.js  # Local dev template
├── core/
│   ├── user.js                         # Stable user ID management (localStorage)
│   └── client.js                       # Statsig client singleton (sync + async init)
├── experiments/
│   ├── renderer.js                     # Apply variants to DOM (text, attr, class)
│   └── bootstrap.js                    # Main orchestrator, config parsing, hydration
└── tracking/
    ├── eventLogger.js                  # Core event logging (Statsig + GA4 bridge)
    ├── exposureLogger.js               # Experiment exposure tracking with dedup
    ├── clickTracker.js                 # Automatic click tracking via event delegation
    ├── engagementTracker.js            # Scroll depth + time on page
    └── init.js                         # Tracking initialization orchestrator

    Adding a New Experiment

    No new JS files are needed. The bootstrap handles everything via config. To add an experiment:

    1. Create the experiment in Statsig console with an obfuscated name (e.g., exp_2026_03_gamma)
    2. Add a target element in your markdown/HTML with an id or CSS selector
    3. Add the experiment binding to the GitHub Secret config:
    {
  "experiments": {
    "cta": {
      "exp_001": { "selector": "#hero-cta-dev", "experiment": "exp_2026_02_beta", "param": "text", "type": "text" }
    },
    "navigation": {
      "exp_002": { "selector": "body", "experiment": "exp_2026_03_gamma", "param": "enabled", "type": "class", "className": "md-tabs--sticky" }
    }
  }
}
    1. Push config update — CI writes the config, bootstrap picks it up automatically

    Binding Types

    Type What it does Required fields
    text Sets element.textContent selector, experiment, param
    attr Sets an attribute value selector, experiment, param, attr
    class Toggles a CSS class selector, experiment, param, className

    Event Tracking

    Events Sent to Statsig and GA4

    Experiments:
- experiment_exposure          # When variant applied to user
- experiment_interaction       # Click on experiment element

Engagement:
- scroll_depth                # Milestones: 25%, 50%, 75%, 100%
- time_on_page                # Thresholds: 10s, 30s, 60s, 120s
- page_view                   # Page loaded/navigated

Navigation/Interaction:
- nav_click                   # Navigation link clicked
- cta_clicked                 # CTA button clicked
- social_share_clicked        # Social media link clicked

      "scrollDepth": [25, 50, 75, 100],

    },
    "googleAnalytics": {
      "enabled": true,
      "sendExposures": true,
      "sendCustomEvents": true,
      "prefix": "statsig_"
    }
  }
}

    Phase 4: Add New Experiments

    Goal: Scale to multiple experiments across both sites

    How to add experiments (config-only, no new JS):

    1. Create the experiment in the Statsig console with an obfuscated name
    2. Add a target element in markup with an id or selector
    3. Add the experiment binding to the site's GitHub Secret config
    4. Test locally by copying the template and adding the binding
    5. Test with URL parameter overrides
    6. Push — CI injects the config automatically

    Priority experiments to consider:

    1. Blog Pagination Count (blog-layout)
    2. Selector: [data-exp="pagination"]
    3. Type: attr, attr: data-pagination-count
    4. Variants: 3, 5, 10 posts per page

    5. Metric: Engagement rate

    6. Navigation Sticky Tabs (navigation)

    7. Selector: body
    8. Type: class, className: md-tabs--sticky
    9. Variants: With/without sticky tabs

    10. Metric: Navigation click rate

    11. Social Share Button Style (visual)

    12. Selector: .blog-social-share
    13. Type: class, className: social-icons-only
    14. Variants: Icon only vs icon + text

    15. Metric: Share click rate

    16. Category Filter UI (blog-layout)

    17. Selector: [data-exp="category-filter"]
    18. Type: class, className: filter-dropdown
    19. Variants: Buttons vs dropdown

    20. Metric: Category navigation rate

    21. TOC Visibility (content)

    22. Selector: .md-sidebar--secondary
    23. Type: class, className: toc-auto-hide
    24. Variants: Auto-show vs auto-hide
    25. Metric: Time on page, scroll depth

    Important: Users see default content until cache is populated (typically after one visit). This is by design — no hiding, no flicker management. The variant appears instantly on return visits.

    Success Criteria: - Multiple experiments running simultaneously - No performance degradation - Default content always visible (no hiding) - Variant applied instantly from cache on return visits - Events tracked for all experiments

    Error Handling & Graceful Degradation

    Principles

    1. Default content in DOM — Always render default variant in markup
    2. Progressive enhancement — Experiments enhance, never break
    3. Fail open — On any error, default content remains visible
    4. Silent failures — Don't show error UI to users
    5. No blocking — Experiments never block page render
    6. No hiding — Never hide content waiting for experiments

    Layered Error Handling

    Level 1: Client initialization failure - getClientSync() returns null - Bootstrap skips experiment application - Default content stays visible

    Level 2: Network timeout (background refresh) - initializeAsync() fails silently - Cache retains previous values - Next visit uses stale cache (still better than defaults)

    Level 3: Experiment application errors - Catch errors during DOM manipulation - Default content stays visible - Error logged for monitoring

    Risk Mitigation

    Risks:

    1. Statsig client not loaded → getClientSync() returns null, defaults shown
    2. GA4 blocked by AdBlock → Wrap in try-catch, fail silently
    3. Performance impact → Use efficient APIs (IntersectionObserver), cache-first init
    4. Event duplication → Track event history, check before logging
    5. Instant nav breaks tracking → Subscribe to document$, reset state properly

    Rollback Plan:

    1. Set tracking flags to false in config (immediate mitigation)
    2. Remove experiment bindings from config (experiments stop, defaults shown)
    3. Remove tracking scripts from mkdocs.yml if needed
    4. Site continues working normally with default content

    Testing Checklist

    Before deploying a new experiment:

    • [ ] Experiment created in Statsig console
    • [ ] Config binding added to GitHub Secret
    • [ ] Target element exists in markup with correct selector
    • [ ] URL parameter override tested locally
    • [ ] Default content looks correct (what users see on first visit)
    • [ ] Variant applies correctly on return visit (cached)
    • [ ] Mobile viewport tested
    • [ ] Instant navigation works (variant re-applies on page switch)
    • [ ] Events tracked correctly (check console with loggingLevel: "debug")
    • [ ] GA integration verified (DebugView)
    • [ ] Staging verification complete
